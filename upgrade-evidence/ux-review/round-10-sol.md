### F1 — P2: Page Reset discards customization without local recovery

**Classification: static recovery/design defect; pictured abbreviated action label.** `ui/menu/PageAppearanceScreen.java:22,42` binds Reset directly to dropping/rebuilding the page editor; `ui/theme/ThemeManager.java:70` removes the page override and marks the manager changed. There is no confirm, captured prior page snapshot or local undo in this route. `ThemeManager.java:257–260` Undo Preset restores the preset's global-setting snapshot, not this removed page. The screen's normal close/removal saves at PageAppearanceScreen:97–98.

**Ordinary-user impact:** one activation can discard a carefully configured page's background/style/color settings. Done/Escape does not cancel the reset. A previously saved profile may offer a separate recovery route, but users are not guaranteed to have one. Images 0071/0080 additionally abbreviate this consequential action as “Reset this pa…”. The label truncation is a clarity issue, not proof of an accidental reset in the recorded run.

**Correction:** make this a recoverable operation: either confirm the named page and explain return-to-inheritance, or snapshot that page and expose a clear Undo reset action until a deliberate next operation. Prefer a fully visible short label such as “Reset page”, with scope explained before commitment.

**Acceptance:** customize multiple page fields; activate Reset by pointer and keyboard at actual 320×240/font2. Cancel preserves exact values, or Undo restores them exactly, including inherited/custom-style flags and image reference. Done/Escape, nested details return and disabled caller styling retain the intended state. Other pages/global values remain unchanged. The complete action label fits and recovery does not close a live container.

### F2 — P2: Resizing a waypoint form preserves values but loses editing context

**Classification: static defect; resize journey unverified.** `map/WaypointEditScreen.java:17–27` saves only strings, clears/recreates EditBoxes and always focuses the first field. `:15` also makes the native initial-focus pass choose Name. There is no focused-field index, caret or selection-anchor capture comparable to `ui/menu/EditBoxDraft.java:6–11` and `ProfileSaveScreen.java:19–23`.

**Ordinary-user impact:** a user editing X, Dimension or Group who resizes the window/changes GUI scale is returned to Name. Subsequent typing can alter the wrong field; editing a selected substring also loses its selection/caret position. Existing values survive, so this is not a claim of wholesale draft-text loss. The test's successful initial Name assertion does not cover reinitialization during editing.

**Correction:** keep Name as the first-open default, but capture/restore each native field's text/caret/selection and the actual focused control during repositioning. Preserve Save/Cancel focus too where appropriate. Reuse the existing draft utility rather than a second selection-anchor implementation.

**Acceptance:** open by keyboard Add and verify Name; focus Dimension or X, select a nonterminal repeated substring, resize actual window and cross the compact/tall column breakpoint. The same field, exact text, caret and selection anchor survive; typing changes only that field. Repeat with an invalid coordinate/error and with Save focused. Save and Cancel still return to the same map/list and retain its view/focus.
