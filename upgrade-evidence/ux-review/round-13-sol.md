## Remaining findings and concrete next work

### F1 — P3: clicking a module setting does not anchor subsequent Tab traversal

**Evidence: live observed + static.** Live33 clicked Sky, then Tab34 focused Pages while the pointer remained on Sky. Hover suppression worked, so this is distinct from review12's stale-help defect. KeyboardNavigation.java:28 clears focused identity on pointerUsed; ClickGui.java:483–484 calls it for each click. ModuleButton.java:136–140 pointerFocus handles color/keybind input but does not adopt generic clicked setting identity into keyboard navigation. Tab without identity starts at the first registered entry, Pages (KeyboardNavigation.java:73–79).

**Impact:** someone inspecting a deep setting with the mouse and continuing by keyboard must traverse unrelated navigation before returning to the area they were editing. It adds effort in a small viewport; no value loss or blocked keyboard route was shown. My live sample was a top setting, so deep-list cost is an inference, not a reproduced tab-count measurement.

**Correction:** retain/adopt the clicked control's logical identity for subsequent Tab traversal while still suppressing pointer help after keyboard intent. Keep ordinary pointer animation behavior.

**Acceptance:** at normal and960×720/GUI3/font2, click a top and a deep toggle/slider, leave pointer resting, press Tab/Shift+Tab and continue with arrows/Enter. Focus should proceed to the neighboring relevant control, reveal its full label/value and dismiss pointer help; restore the initial value afterward. Preserve input editing and offscreen reveal semantics.

### F2 — P3 discovery friction: expanded custom editor is hidden behind the named chooser

**Evidence: live observed + static.** Two clicks44/45 in the visibly truncated ID field only focused it. Its tooltip said Advanced: custom dimension ID, which did not explain the expanded route. The successful path was Dimension→Custom Id46/47. WaypointEditScreen.java:31–33 creates that route;49 labels the inline field but does not link it to expanded editing. TextValueScreen itself was clear once opened.

**Impact:** an advanced user whose immediate goal is to inspect a long existing ID may first attempt caret scrolling in a tiny field, unaware that a full-width editor exists behind the world chooser. Named common-world tasks work well. This is discovery friction, not inaccessible data or a failed complete task, and one agent's hesitation does not establish population prevalence.

**Correction:** add an explicit Expand/Edit full value action beside the inline ID/Hex, or make the help name the chooser→Custom route. Preserve direct inline editing for users who prefer it.

**Acceptance:** ask an unfamiliar user to inspect/change a long existing ID at compact size without telling them to open the world chooser. Full value, Use and Cancel should be discoverable, retain exact draft/caret/selection through resize, and preserve unrelated errors. Repeat for custom Hex; do not complicate the current named-world/color tasks.
