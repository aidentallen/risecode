# 0.24.0 — Performance modes and retained-work reductions

Open the small footer settings popup and choose **Performance**. Off is the default.
Conservative disables GUI blur/glow, soft shadows and menu particles while keeping full
cosmetic detail and density. Balanced also reduces procedural detail and halves cosmetic
particles. Strong suppresses cosmetic particles and trails while retaining tail motion and
trail history for restoration when switched Off. All presets reduce background
work and cache budgets. Custom exposes each reduction independently.

Editing an individual control copies the effective preset into Custom. Switching presets
retains your last Custom configuration. Switching Off restores the selected effects; no
module, appearance profile, outfit, cape, imported model, target limit or outline resolution
is rewritten. Preferences live globally in the additive `ui.performance` object.

Reduced rings and hearts keep their dimensions. GUI shadows become crisp. Map recording
keeps its existing enabled setting and explored disk data; reduced work refreshes more
slowly. Active cosmetics, visible previews and resources referenced by pending draws can temporarily exceed
cache budgets. Unused resources are evicted first, with working-set overages reported.

HUD measurements, class lookups and unchanged nametag equipment are cached. Dynamic item
appearance, including clocks and compasses, still refreshes at tick cadence. Native label
text ordering is cached by content, font, language and resource generation. ESP geometry is
packed into immutable arrays with lazy legacy inspection views. Silhouette quads are batched
by render type; targets retire after forty unused client ticks at a frame boundary.

Minecraft 26.2 and Java 25 remain required. Validation and direct-counter performance
results are recorded in [remediation.md](../remediation.md). Synthetic players do not
establish live multiplayer performance.

## Independent work and cache budgets

| Resource | Normal | Reduced |
| --- | --- | --- |
| Map capture per tick | 32 columns / 1.5 ms | 16 columns / 0.5 ms |
| Map CPU cache | 512 tiles / 64 MiB | 256 tiles / 32 MiB |
| Map GPU cache | 512 tiles | 128 tiles |
| Resource previews | 48 cached / 16 pending | 24 cached / 8 pending |
| Unused cosmetic assets | 16 entries / 64 MiB | 8 entries / 32 MiB |

Reduced background work also limits map completion processing to eight completions and
0.25 ms per tick. Individual engine calls cannot be preempted by these deadlines. Pending
writes and waypoint/death persistence keep their existing ordering. Cache accounting reports
entries, decoded payload, owned native images and owned GPU texture payload separately;
JVM heap and backend/driver memory are separate measurements.

## Measured comparison

Three alternating 0.23.0 / 0.24.0 production-JAR repetitions, each with ten seconds of
warmup and thirty seconds of measurement per scene, reduced direct render-thread allocated
bytes/frame by **32.7%** with 24 synthetic equipped players and **25.4%** with common-block
ESP. Both ran with Performance **Off**. Median p95 render time improved in all six scenes;
a single movement/map p95 increase did not repeat in the next two pairs. These are local
fixture results, with live multiplayer remaining a separate validation gap. Full counters,
GC observations and renderer/lifetime validation are in [remediation.md](../remediation.md).

The packaged production JAR passed native checks on vanilla OpenGL, Sodium OpenGL,
Sodium/Iris with Complementary Unbound r5.9.3, and Sodium Vulkan, with twenty reload/resize
cycles on each. A thirty-minute Sodium OpenGL session recorded 270.6–274.0 MiB post-GC
heap, bounded work queues and zero sampled cache overages. These owned-resource and heap
observations are separate from the render-thread allocation comparison above.
